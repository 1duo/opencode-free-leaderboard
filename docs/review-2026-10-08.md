# Review and execution record — OpenCode client

All current evaluation commands use the installed OpenCode 1.18.31 client. Generation does not post directly to Zen. Official catalog and pricing GET requests remain part of discovery.

## Protocol corrections

Earlier direct API and native experiments are archived privately and excluded from the current results. The earlier native adapter flattened system/user messages and set `steps: 1`, causing the client to inject its maximum-step summary instruction on the first response. Those results cannot establish an isolated model or transport effect.

Protocol revision 3 uses a fresh session with a fixed primary benchmark agent, no step limit, no tools or plugins, no auxiliary agents, and no compaction. Original benchmark system instructions and user questions retain their roles. OpenCode's environment context remains and is disclosed. Only exact officially verified zero-price Zen IDs can be selected; other providers and paid fallback are disabled. The client and effective configuration create a separate evaluation epoch.

A dedicated authenticated loopback server is started through the real installed client. Its agent configuration, model route, zero-price metadata and output settings are checked. Client-reported cache and reasoning counts are counted once. Responses are saved before grading; unknown outcomes are not replayed. Initial attempts and observed retry events receive committed reservations. Retries are bounded and the private server is stopped during backoff when the allowance is exhausted. This is a client-observed dispatch count, not an audit of every provider HTTP request.

Future client sessions, configuration and caches are isolated beneath private state. The first revision-3 screen also left sessions in OpenCode's existing local history; those database files now have restrictive permissions. Its saved sessions were audited locally without publishing prompts or responses.

## Verification

Focused checks exercised eligibility and prohibited-model gates, role preservation, archived-record exclusion, resumed screen generation without duplication, retained grading failures, retry limits, missing usage, output-cap overruns, quota deferral, ambiguous outcomes, and malformed completions. Ruff and JavaScript syntax checks passed. The actual compatibility run also exercised the real OpenCode client and pinned Docker grader.

Space Bunny completed six synthetic probes and four held-out benchmark questions under revision 3. Combined output-cap semantics were verified by the synthetic truncation probe. Other supported free IDs returned access restrictions, deprecation, or provider errors. These failures remain unscored and cannot lower capability scores. Switching to the client does not guarantee access to every advertised free model.

## Screen and release status

The current screen uses the same frozen question IDs and pinned graders: 20 LiveBench spatial/zebra questions dated 2024-11-25 and 40 Python LiveCodeBench release_v6 problems. It generates fresh answers; previous API, native, and pilot answers are not reused. Its scores remain unranked subsets.

Space Bunny completed all 60 questions: LiveBench 13/20 (65%) and LiveCodeBench 25/40 (62.5%). All 60 saved sessions matched the original benchmark system/user content, contained exactly one assistant completion and no tools, selected the exact free model, reported zero cost, and stayed within the 4,096-token combined output cap. Each question had one recorded generation attempt. Sixteen responses were truncated and graded as returned. The model does not advertise temperature support, so OpenCode omits that setting; this is disclosed by the “where supported” protocol qualifier.

There are no full 80-question rankings or 240-question confirmations. Authenticated GPQA access is missing, and the required three-model pilot has not passed. Practical agent suitability remains outside this milestone. Review cannot establish absence of training contamination or silent changes behind model aliases. Bootstrap intervals describe question sampling, not repeated-generation variability.
